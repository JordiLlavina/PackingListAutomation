# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Qué es este proyecto

Generador de packing lists en Excel para clientes de un proveedor de marroquinería (Punto Tres). A partir de un JSON de envío (pegado a mano o extraído de fotos con la API de Anthropic), asigna palets, infiere pesos que faltan y genera un `.xlsx` por grupo rellenando la plantilla real de cada cliente con Apache POI. Incluye un asistente web (Spring Boot + Thymeleaf) de 3 pantallas y un volcado de albarán para el ERP.

Stack: Java 17, Spring Boot 3.5 (web + thymeleaf + validation), Apache POI, Jackson, SDK Java de Anthropic. Idioma del código y la documentación: **español** (nombres de clases en inglés, javadoc/comentarios/UI en español).

## Comandos

```bash
mvn test                                      # toda la suite
mvn test -Dtest=PackingListGenerationServiceTest   # una clase de test
mvn -q compile exec:java                      # prueba manual: Main.java, flujo completo → excels en target/
mvn spring-boot:run                           # asistente web en http://localhost:8080
```

- El test end-to-end `flujoCompletoGeneraExcelsAbribles` deja excels reales en `target/` para inspección manual.
- El modo CLAUDE de la pantalla de entrada (fotos o PDFs → JSON) necesita la variable de entorno `ANTHROPIC_API_KEY`. Sin ella la app arranca igual y el resto de modos funciona (cliente HTTP perezoso).
- **Windows**: matar `mvn spring-boot:run` no mata el proceso `java` hijo y el 8080 queda ocupado. Liberarlo: `netstat -ano | findstr :8080` + `taskkill /F /PID <pid>`.
- La portada es `/menu`; el asistente de packing list vive en `/packing-list` y `/` redirige al menú.
- `EscandallosFlujoRealTest` deja `target/Escandallos ICSUITE.xlsx` con los dos escandallos reales, para compararlo a mano con el ejemplo de `docs/Procesado Escandallos ICSUITE/`.

## ⚠️ Números de pedido y destinaciones por cliente — LEER ANTES DE TOCAR NADA DE ESTO

**Esta sección es de lectura obligatoria antes de escribir código que toque
destinaciones de cliente o números de pedido.** No se deduce del código ni de
los nombres de las clases, y equivocarse aquí escribe un número de pedido
erróneo en un documento que va al cliente.

Los dos hechos, **verificados contra los ficheros de pedido reales**
(`EAN PUNTOTRES H26.xlsx` y `APC_PEDIDO_FALL26.xlsx`), no supuestos:

| | AMI | APC |
|---|---|---|
| Cómo lo llama el cliente | **PO** (`07704 CH`) | **Document d'achat** (`4100128863`) |
| Granularidad del número | **UNO por `referencia` + `destinación`** | **UNO por `referencia` + `color` + `destinación`** |
| Por destinación sola | **VARIOS** (12 en CHINA, 15 en JAPAN, 25 en PARIS) | **VARIOS** (de 4 en Australia a 16 en Wholesale) |
| ¿Se puede propagar el número entre colores de una referencia? | **SÍ** | **NO, nunca** |

**Lo que esto permite y lo que prohíbe:**

- En **AMI** el PO no depende del color: todos los colores y tallas de una
  referencia que van a la misma destinación comparten PO. Por eso se puede
  rellenar solo en las filas que el excel de pedido no reconoce, copiándolo de
  una fila hermana de la misma referencia (`ObjetivosPedidoAmi`). Medido: 52
  claves `referencia+destinación` en el fichero real, **ninguna** con más de un
  PO; y lo mismo bajando a `referencia+color+talla+destinación` (151 claves,
  ninguna con más de uno).
- En **APC** eso sería un error: un `Document d'achat` es una destinación, un
  artículo **y un color**, con una fila por talla, así que dos colores de la
  misma referencia a la misma destinación llevan números distintos. Copiar el
  de un color al otro pondría en el packing list un pedido que no es el suyo.
  Por eso `ObjetivosPedidoApc` cruza por el `CODE` de tres dígitos de cada fila
  del taller y **no propaga nada**.

**El error a evitar** es leer "un PO por destinación" como "un PO para toda la
destinación". Es falso en los dos clientes: una destinación recibe decenas de
pedidos, uno por artículo. Lo que es único es el número **dentro de una
referencia** (AMI) o **dentro de una referencia y un color** (APC).

Si algún día hay que volver a comprobarlo, se mide leyendo los dos excels de
pedido de `src/test/resources/ejemplos/` y contando claves distintas; no se
deduce de los JSON de ejemplo, que son fixtures inventados.

## Arquitectura (lo esencial)

Pipeline de servicios Spring sin estado, encadenados por `PackingListController` (web) o `Main.java` (prueba manual):

```
EnvioInput (calco del JSON)
  → EnvioImportService      expande rangos de cajas, valida sin bloquear
  → PaletAssignmentService  asigna palet por rango de nº de caja
  → WeightInferenceService  infiere pesos que faltan (taras de application.yml)
  → PackingListGenerationService  despacha al builder del cliente → excels
  → VolcadoErpGenerationService / VolcadoErpExcelBuilder  albarán para el ERP
  → EtiquetasGenerationService → GeneradorEtiquetasCliente (AmiEtiquetasGenerador)
      → excels de etiquetas de caja (mismo paso que los packing lists)
```

Tres capas de modelo, separadas a propósito (ver ARCHITECTURE.md):
1. `model/EnvioInput` — calco literal del JSON de entrada, frágil a propósito; solo `EnvioImportService` lo conoce.
2. `model/CajaData`, `DestinoData`, `PaletData` — dominio: una caja física por objeto; los servicios trabajan solo contra esto.
3. `PackingListData` — vocabulario de la plantilla Excel de un cliente concreto.

**Multi-cliente**: `GeneradorPackingListCliente` es la interfaz; `AmiGenerador`/`AmiExcelBuilder`, `ApcExcelBuilder` y `GenericoExcelBuilder` la implementan, y `PackingListGenerationService` despacha según `ClienteConfig.getPlantilla()` (`TipoPlantilla`: AMI, APC, GENERIC). El catálogo de clientes vive en `application.yml` (bloque `packing-list.clientes`): **añadir un cliente de plantilla GENERIC es solo configuración** (nombre-legal + direccion-entrega), sin tocar Java. Igual con las taras: un tamaño de caja nuevo es una línea en `packing-list.taras`.

**Nombre de los excels de packing list**: APC y GENERIC usan `PKL_<destino>_<factura>.xlsx`, pero **AMI tiene el formato que exige el cliente** y vive en `AmiNombreFichero`: `<fecha envío yyyy.MM.dd>_PUN_<product order>_<referencia>.<color>_<temporada>_<destinación abreviada>.xlsx`. La destinación se abrevia (FRANCE/FRANCIA/PARIS → FR, CHINA, JAPAN) y una destinación desconocida no bloquea: va en mayúsculas y sin espacios. Los campos que falten se omiten en vez de dejar separadores sueltos.

**Envíos que van sueltos, sin palet** (`CajaData.SIN_PALET`, `PaletAssignmentService.MAX_CAJAS_SIN_PALET`): de 1 a 3 cajas **físicas** una destinación se manda suelta, sin palet, así que su hoja de palets no existe y no es un dato que falte. `PaletAssignmentService` les estampa el palet **0** y se calla: ni aviso de "no hay palets en la distribución", ni la alerta roja de "no cae en ningún rango", ni el aviso de etiquetas de que falta la hoja de palet (APC y AMI). Lo que no se deduce del código:

- El palet **0 es un número y no `null`** a propósito. `null` significa "esta caja debería ir en un palet y no se sabe en cuál", que es lo que la revisión pinta en rojo; y como `recalcularCajasSinPalet` vuelve a derivar esa lista **del dato** tras cada edición, con `null` la alerta reaparecería en cuanto el usuario tocara cualquier campo. Con el 0 se ve en la columna PALET, sobrevive a los recálculos y no vuelve.
- Un palet 0 **no es un palet en ningún documento**: `ApcExcelBuilder` y `GenericoExcelBuilder` lo mandan al bloque de cajas sueltas (`CajaData.vaSuelta`), que no suma tara ni volumen de palet. Contarlo pondría 10 kg y 0,168 m3 inventados en el peso y el volumen brutos que lee el cliente y la aduana.
- El rótulo de ese bloque en el packing de APC es **`NO PALLET`**, en inglés como el resto de la plantilla del cliente. En GENERIC sigue diciendo `SIN PALET` porque esa plantilla no se ha revisado; si algún día se usa de verdad con un envío suelto, hay que traducirlo igual.
- Se cuentan **cajas físicas** (números de caja distintos), no líneas: una sola caja con cuatro artículos dentro sigue yendo suelta.

**Destinos padre de APC**: `WHOLESALE` y `RETAIL` agrupan destinaciones hijas (`AUSTRALIA`/`WHOLESALE`/`CHINE FRANCH` y `RETAIL`/`WHOLESALE CONCESS`) que se tratan como el padre: mismo fichero, misma hoja y misma dirección, y la hija solo sobrevive en la columna `DESTINATION` (si la línea no trae `canal`, se rellena con ella). Lo hace `ResolutorDestinosPadre` tras importar y **antes** de asignar palets, fusionando en un solo `DestinoData` las hijas del mismo padre —lo que además evita dos ficheros con el mismo nombre, que `/descargar/{nombreFichero}` resuelve con `findFirst()` y dejaría el segundo inalcanzable en silencio. **Nunca renumera cajas ni palets**: si dos hijas repiten un número, avisa y lo deja, porque ese número va pegado al bulto. Añadir una hija es una línea de `destinos-hijo` en `application.yml`. `C-LOG` era el nombre viejo de `WHOLESALE` y ya no existe.

**Livraison code de APC**: lo genera `LivraisonCode` (`PUN` + fecha de envío `yyyyMMdd` + `abreviatura` del padre + contador), no el JSON — el `livraisonCode` de entrada **se ignora**. Las abreviaturas del yml (WH, RT, UST, JPT, KRT) son las de la columna `Catégorie de stock` del pedido real; un destino sin abreviatura cae a su nombre en mayúsculas y sin espacios, con aviso. El contador arranca en 1 porque no hay historial de envíos, así que el código se muestra **entero y editable en la cabecera de cada destinación** de la revisión, no como columna de la tabla: como columna se repetiría en cada fila y ensuciaría el criterio de compactación.

**Pie del packing list de APC**: seis líneas con el **rótulo en la columna D y el valor en la E** (`PALLETS`, `CARTONS`, `CARTON WEIGHT`, `CARTONS VOLUME`, `GROSS WEIGHT`, `GROSS VOLUME`), tal como las pide el ejemplo real del cliente (`docs/Packing Lists/apc-bags-and-belts-complete-example.xlsx`); antes eran cinco frases enteras metidas en la D ("TOTAL GROSS WEIGHT (CARTON + PALET)  406,20 KG"). Dos cosas que no se ven en el ejemplo: los pesos y volúmenes se escriben como **números** y por eso hay que redondearlos al escribirlos (2 decimales el peso, 3 el volumen), o la suma en coma flotante deja un `378,6400000000001` en una celda que lee el cliente; y **`GROSS` es siempre cartones + palets**, en peso igual que en volumen. Ojo: el ejemplo del cliente trae los dos pesos **intercambiados** (`CARTON WEIGHT` 406,2 y `GROSS WEIGHT` 378,64, cuando 406,2 es el bruto con las taras de palet) y el recuento de `PALLETS` puesto a mano; el código sigue la semántica, no esos números. `PALLETS` y `CARTONS` llevan el recuento y el desglose de medidas entre paréntesis (`53 (60x40x40cm)`, `2 (1*80x120x130+1*?)`), con `cm` solo en los cartones porque así está en el ejemplo, y `0` a secas cuando no hay palets.

**Número de pedido y referencia de APC**: de las hojas manuscritas los dos llegan **incompletos** — del pedido, sus **tres últimos dígitos**; de la referencia, lo que escribe el operario (`67043`, `F63023`), que es un **sufijo** del `Article` real (`PXCEI-F67043`). `PedidoCompletionService` busca la fila en el excel de pedido del cliente (`ApcPedidoExcel.filasPara`, sufijo de `Article` + esos tres dígitos; una fila exacta por referencia gana sobre las de solo-sufijo) y, si es **única**, estampa el pedido Y la referencia enteros; en el fichero real todas las referencias de las hojas escaneadas son unívocas (`ApcPedidoExcelTest` lo ancla). La hoja se localiza exigiendo **tres** cabeceras (`Article`, `Document d'achat` y `Notre référence`), porque otras dos hojas del libro tienen las dos primeras. Sin excel, sin fila o con varias candidatas: aviso y se deja lo que llegó, nunca un dato adivinado. **Corre solo al importar**, igual que `PaletAssignmentService`: reejecutarlo en los recálculos de la revisión machacaría lo tecleado a mano.

**Extracción por imágenes** (`ClaudeEnvioExtractionService`): acepta **fotos y PDFs** (los PDFs viajan como `DocumentBlockParam`; `bloquesDe` es el seam testeable). Las hojas reales son **notas manuscritas en taquigrafía de operario**, no tablas — hojas de ejemplo en `docs/Packing Lists/*IMAGENES.pdf`, análisis completo y catálogo de fallos en [docs/Packing Lists/analisis-hojas-manuscritas.md](docs/Packing%20Lists/analisis-hojas-manuscritas.md), y la guía de escritura para el operario en [guia-operario-packing-manuscrito.md](docs/Packing%20Lists/guia-operario-packing-manuscrito.md). El prompt se monta **núcleo + bloque por `TipoPlantilla`** (`promptPara`): el núcleo enseña la taquigrafía (rangos, cajas mixtas "TODO Nº 1", tachados = no existen, apóstrofo decimal, **barra `/` que separa referencia/modelo/color en la línea de cabecera**) y el bloque lo específico del cliente (AMI: partir `UBL029.AL0216.2221` en referencia+color, numeración continua; APC: referencia y pedido parciales a propósito, hoja por destinación, numeración que reinicia). El JSON extraído trae dos campos que el pegado a mano no suele traer: `avisos` (dudas de lectura → `EnvioImportado.getAvisos()` con prefijo "Lectura de las hojas:") y `resumenPalets` (recuentos declarados, "wh. 5 palet"). `ValidadorResumenExtraccion` contrasta ese resumen con lo extraído y es **la única validación del proyecto que bloquea** (vuelta a la entrada sin pasar a revisión, con el JSON extraído volcado al textarea en modo JSON): un descuadre ahí significa casi siempre que falta una hoja en el escaneo, que no se arregla en la revisión. Recuento sin reparto de cajas = aviso, no bloqueo (los palets se completan en la revisión); `parsear` normaliza el apóstrofo decimal (`13'52` → `13.52`) como red del prompt, y el importador limpia el prefijo de talla manuscrito (`t75`/`+75` → `75`).

La **barra de la cabecera** (regla 2 del núcleo) es una convención que se le pide al operario, y el prompt la trata con tres cautelas que no son opcionales (`elPromptEnsenaLaBarraDeLaCabeceraSinHacerlaObligatoriaNiGlobal` las ancla): **no es obligatoria** —las hojas ya escritas no la llevan y sin ella se sigue separando con las reglas del cliente—, **solo vale en la línea del `MOD`** —la barra ya significa "unidades/talla" en las líneas de caja (`122/75`) y separa filas en la tabla de palets (`1 1-12 / 2 13-24`), así que sin acotarla el modelo puede reinterpretar cantidades— y en **AMI el patrón de puntos manda sobre ella** (`UBL029.AL0216.2221 / chocolat` sigue dando color `2221`, no `chocolat`). Donde de verdad paga es en APC: `sac Le Neige CLOU CAMEL` no se puede partir en modelo y color sin conocer el catálogo de colores del cliente.

**Presupuesto de tokens de la extracción**: el razonamiento y el JSON de salida **comparten el techo de `max_tokens`**, y descifrar ocho páginas de caligrafía consume mucho razonamiento: con el techo de 16.000 que había, la respuesta llegaba cortada (`stop_reason: max_tokens`) y el usuario veía "se ha cortado por longitud" sin ningún JSON. El techo es ahora holgado (32.000) y el razonamiento se acota con **`outputConfig(effort)`**, NUNCA con `ThinkingConfigEnabled.budgetTokens`: Opus 4.8 solo admite `thinking.adaptive` y rechaza `thinking.enabled` con un **400 en tiempo de ejecución** que ningún test de dominio ve (`elRazonamientoEsAdaptativoConEsfuerzoYTechoDeSobra` lo ancla). Medido contra el PDF real de APC: **~4 minutos** y 53 referencias en 5 destinaciones. La petición va en **streaming acumulado** (`createStreaming` + `MessageAccumulator`) y el cliente lleva timeout de 15 min: no es por enseñar nada al usuario, es lo que permite pedir un presupuesto grande sin morir por timeout de lectura.

**Plan B manual**: [docs/Packing Lists/prompts-para-copiar.md](docs/Packing%20Lists/prompts-para-copiar.md) trae los tres prompts listos para pegar en claude.ai y volver por el modo JSON. Está **generado desde el código** y `PromptsParaCopiarTest` falla si se queda viejo: si el doc y el código divergen, los dos caminos dan resultados distintos sin que nada avise. Para regenerarlo, editar el doc a mano no vale — hay que copiar la salida de `promptPara(...)`.

**Excel de pedido en la entrada**: los clientes con `pedido-cliente: true` en `application.yml` (APC y AMI) muestran un input de fichero opcional en `/packing-list`. Se guarda en `EnvioEnCurso` y de ahí lo saca todo lo demás; es **la única** vez que se pide. Como ya no hay pantalla que confirme cuál se subió, la tarjeta de etiquetas de `/resultados` nombra el fichero con el que se generaron: el pedido equivocado daría etiquetas malas sin decir nada.

**Temporadas guardadas** (`persistence/TemporadaGuardada`, `ArchivoTemporadas`, pantalla `/temporadas`, enlace "Guarda Temporadas y Ficheros" en el menú): el excel de pedido de un cliente es **el mismo documento durante toda una temporada**, así que se guarda una vez —cliente + nombre de temporada + excel— y en la entrada basta con elegirla en un desplegable que sale **al lado del cliente**, con un lápiz que lleva a mantenerlas. Tres cosas que no se deducen del código:

- El fichero se guarda **entero en la base de datos**, no como ruta al disco: una ruta se rompe en cuanto alguien mueve la carpeta y el fallo aparece a mitad de un envío, mientras que con la copia dentro las temporadas viajan con `./datos` de un ordenador a otro.
- Al elegir una temporada, el campo libre **Temporada se esconde** y lo rellena el desplegable: dos campos con el mismo rótulo a la vez dejarían sin saber cuál manda. El desplegable trae siempre `-- otra temporada --` para el envío de una temporada que aún no está guardada.
- El envío usa el excel guardado **solo si es del cliente elegido** (`ArchivoTemporadas.paraElEnvio`). El desplegable se rellena en el navegador, así que cambiar de cliente después de haber elegido temporada dejaría enviado el id de la de otro y el packing saldría con el pedido equivocado, que no se ve hasta que el documento llega mal. Un excel subido a mano **manda sobre el guardado**, y una temporada que ya no existe deja aviso, nunca silencio.

Solo se ofrecen los clientes con `pedido-cliente: true`, que son los únicos con un fichero que ahorrar. Los atributos de la pantalla de entrada los monta `AtributosEntrada` para los dos controladores que la pintan (el del asistente y el del taller): con una copia en cada uno, un dato nuevo se añade en una y desaparece en silencio al volver por el otro camino.

**Etiquetas de caja** (`service/etiquetas/`): estrategia propia `GeneradorEtiquetasCliente` despachada por **clave de cliente** (no por TipoPlantilla); cada implementación declara qué destinaciones soporta y qué archivos necesita (`CampoEtiquetas`). **No hay paso intermedio**: se generan dentro del mismo `POST /generar` que los packing lists, y `CampoEtiquetas` ya no pinta inputs — le dice al controlador qué sacar de la sesión. Lo que no se pueda resolver sale como aviso en `/resultados` y deja el envío sin etiquetas, nunca sin packing lists. Implementado: AMI (China/Japan/France; hoja por destinación, par de etiquetas A4 por caja, más su hoja de palets) y APC (JAPAN, KOREA, D. USA, WHOLESALE y RETAIL, **una plantilla por destinación** y dos hojas por libro, cajas y palets; sin archivos extra, porque el pedido y el Livraison code ya vienen rellenos del packing list). `IVRY` sigue sin etiqueta: genera packing list y avisa. Plantillas en `src/main/resources/client-labels/` — misma regla que las de packing list: **no editarlas sin revisar su builder** (`AmiEtiquetasExcelBuilder`/`AmiEtiquetaLayout`, cuyas coordenadas ancla `AmiEtiquetaLayoutTest`; `ApcEtiquetasExcelBuilder`/`ApcEtiquetaLayout`, las de APC).

**Etiquetas de palet de AMI**: una hoja más (`Etiquetas Palets CHINA/JAPAN/FRANCE`) dentro del mismo libro de etiquetas de caja, con **dos etiquetas por A4** (media página cada una, salto de página cada dos palets). Sus coordenadas son constantes compartidas de `AmiEtiquetaLayout` (`FILA_PRIMER_PALET`, `ALTURA_BLOQUE_PALET`, `FILA_PALET_COLIS`, `FILA_PALET_PESO`) porque las tres hojas son idénticas salvo los textos fijos del destinatario. Tres cosas que no son obvias: el bloque **arranca en la fila 1**, no en la 0 (encima va un contador que el cliente apunta a mano, se blanquea y no se replica — por eso existe `BloqueEtiquetaModelo.capturar(hoja, filaInicio, altura)`); la plantilla trae **dos bloques de ejemplo** y lo que sobre tras el último palet **hay que borrarlo**, o la etiqueta de ejemplo del cliente se imprime y acaba pegada en un bulto; y los rótulos de la columna B son **bilingües y multilínea** (`EXPEDITEUR\n(Shipper / Sender)…`), así que buscarlos por texto exige comparar solo la primera línea.

El campo palet es **opcional**, y basta con que **una** caja de la destinación no lo traiga para que ese excel salga **sin hoja de palets** y con aviso: una hoja a medias se imprime y se pega igual que una completa, y quien la mire asumirá que están todas. Es más estricto que APC, que genera la hoja aunque esté vacía. Un peso que falta sí es distinto: solo deja en blanco su celda. El rango `Nº X à Nº Y` se lee de **las cajas**, no del `cajaInicio..cajaFin` del `PaletData`: ese es el del JSON original y se queda viejo en cuanto el usuario corrige un palet en la revisión. El peso es la suma de las cajas físicas más la tara (10 kg si el JSON no la trae), como en APC, pero se rotula `Kg` y no `KGS` porque es lo que pone la plantilla de palet.

**Una etiqueta de APC lleva TODOS los artículos de la caja**: `Order N°`, `Reference` y `Colour` se concatenan con `" / "` en el **mismo orden** (un artículo = referencia + color, en el orden del packing list), para poder leerlas en paralelo columna a columna. El pedido no se puede heredar de la línea líder como se hacía: en APC un `Document d'achat` es una destinación, un artículo **y un color**, así que una caja con cuatro artículos lleva cuatro pedidos distintos y quedarse con el del líder pone en la etiqueta un pedido que no es el de los demás. Un artículo sin pedido deja `NOT FOUND` **en su posición**, no un hueco. Lo que sigue siendo de un solo artículo (el líder) en una caja de cinturones son `SIZE` y `PIECES BY SIZE` —en una etiqueta no cabe más de un desglose por talla—, y de eso avisa `Mezcla de referencias/colores`. El `Livraison code` sí es único: es de la destinación entera.

**La fila de `Reference` de la plantilla de USA no es la de su rótulo**: en `apc-etiquetas-usa.xlsx` la celda de valor está **combinada** (`C12:C13`) y el rótulo cae en la fila de abajo, así que `ApcEtiquetaLayout.USA.filaReferencia()` es **11 y no 12**. Escribir en la fila del rótulo no da error ni celda vacía —Excel ignora lo escrito en una celda tapada por una combinación—: se queda a la vista la referencia de ejemplo de la plantilla, que es de otro artículo, y el fallo solo se ve abriendo el excel. `cadaFilaEsLaDeSuRotuloResolviendoLasCeldasCombinadas` lo ancla para las cinco plantillas, buscando cada rótulo en la columna B y resolviendo la combinación de su celda de valor.

**RETAIL y WHOLESALE de APC comparten maquetación pero no plantilla**: las dos etiquetas van al mismo almacén (Crosslog) y el cliente solo partió el fichero para que se imprima `RETAIL` o `WHOLESALE` en la línea `DESTINATION`; todo lo demás —filas, celdas combinadas, anclajes del logo— es idéntico. Por eso `ApcEtiquetaLayout.RETAIL` repite las coordenadas de `WH_CROSSLOG` y **ese estático es lo único que distingue haber abierto una plantilla u otra**: apuntar RETAIL al fichero de Crosslog pasaría cualquier aserción de celdas, así que se ancla aparte (`retailYWholesaleCompartenCoordenadasPeroNoPlantilla` y la aserción de `DESTINATION` en `ApcEtiquetasGeneradorTest`).

Cada etiqueta lleva **dos imágenes**, no tres: la **imagen compuesta** del artículo (los cuatro textos de la etiqueta de artículo más su EAN-13, generados en un solo PNG por `ImagenEtiquetaArticulo`, que solo habla del **primer** artículo de la caja) y el Code 128 del `EAN128` del excel de pedido. El Code 128 del PO **ya no existe**: el cliente lo quitó de su plantilla. `COLOR CODE` en la etiqueta es **solo el código** (`221`); el color completo (`221 DARK COFFEE`) va dentro de la imagen compuesta y en la hoja extra — `AmiPedidoExcel.FilaPedido` da los dos. `REFERENCE` y `ORDER NUMBER` son celdas combinadas en la plantilla nueva (ver más abajo por qué importa para `shrinkToFit`). La dirección de JAPAN se extrae **por su anclaje** en la plantilla, no cogiendo el primer PNG del libro: la plantilla trae dos PNG (el mock de la imagen compuesta y la propia dirección) y coger "el primero" sacaría el equivocado.

**El código de barras nunca se reescala**: se genera ya con la altura de barras que le toca (`CodigoBarrasEan13.png(ean13, proporcion)`) y se pega 1:1 con `Graphics2D.drawImage`; reescalarlo con interpolación lo deja bonito en pantalla e ilegible para un lector físico. La proporción barras:dígitos (5,5:1) sale medida del mock del cliente y deja las barras a ~42% de la altura nominal de un EAN-13 en la maqueta del cliente — **eso solo lo puede verificar un lector físico, ningún test lo cubre**. `CodigoBarrasEan13.png(String)` sin proporción sigue saliendo **byte a byte igual** que antes de esta feature, porque lo usan caminos ya en producción (hay un test que lo fija). La zona muda (`doQuietZone(true)`) es parte del símbolo, no un margen decorativo: sin ella muchos lectores no leen.

**Los dos EAN de las etiquetas de AMI** salen del excel de pedido con **clave exacta** `ARTICLE`+`COLORIS`+`TAILLE`+sufijo de PO (en el fichero real esa clave identifica una sola fila de 151; el color es obligatorio porque hay 59 claves con varios colores). Si no hay fila exacta: aviso y etiqueta sin esos códigos, nunca la fila de otro PO. La talla es la de la **línea líder** de la caja, porque en una caja de cinturones con varias tallas solo cabe un par de EAN. El `EAN128` se pasa a Code 128 **verbatim**, nunca compuesto: lleva dentro el EAN13 y el PO, y en el fichero real hay 8 filas donde eso no cuadra con sus propias columnas — se avisa y se imprime igual, porque es el código del cliente el que espera su escáner. `AmiPedidoRealTest` ancla todo esto contra el fichero real.

**Varios artículos en una caja** (`ArticulosDeCaja`): una caja física puede
llevar varios artículos y la etiqueta ya no los colapsa a la línea líder. Un
artículo es referencia+color en bolsos y referencia+color+**talla** en
cinturones (cada talla es un SKU con su propio EAN-13). En **bolsos** la
etiqueta concatena `REFERENCE`, `COLOR CODE` y `QUANTITY` con `" / "` en el
orden del packing list —`SIZE` sigue siendo `U`— y `AjusteFuente` encoge la
fuente si el texto no cabe (tamaño calculado con suelo de 8 pt **y**,
solo cuando el estilo original no tiene `wrapText` ni la celda está
combinada, `shrinkToFit` como red de seguridad adicional). **Excel ignora
`shrinkToFit` tanto en celdas con `wrapText` como en celdas combinadas.** En
las cuatro plantillas de **APC** el motivo es `wrapText`. En **AMI**, con la
plantilla nueva, la celda `REFERENCE` está **combinada**, así que ahí lo único
que protege el texto es el tamaño calculado de `AjusteFuente` — igual que en
APC, aunque por un motivo distinto. Los **cinturones no cambian de valor** en
`SIZE`/`QUANTITY`: `SIZE` se escribe sin pasar por `AjusteFuente` y nunca
encoge, pero `QUANTITY` sí pasa por él como cualquier caja, así que su fuente
puede encoger si el texto no cabe (`AjusteFuente` se aplica por celda, no por
tipo de caja).
Como en una etiqueta solo cabe un par de EAN, los artículos 2..N van a la hoja
`CODIGOS BARRAS EXTRA` (`HojaCodigosBarrasExtra`, sin plantilla propia, maquetación
en constantes) del mismo libro de la destinación, con un aviso al usuario de que
hay una hoja más que imprimir. Usa **la misma rejilla que las etiquetas de
artículo** (`RejillaEtiquetas`), 10 artículos por A4, con tres columnas por
bloque: caja, EAN-13 y EAN128. Solo AMI: **APC no imprime códigos de barras**,
solo hereda la concatenación.

`EtiquetaArticulo`, `RejillaEtiquetas` y `BloqueEtiquetaArticulo` viven en
`service/etiquetas/` (no en `service/etiquetasarticulo/`) y los comparten los
dos flujos, el de etiquetas de caja y el de etiquetas de artículo: **tocar uno
afecta a los dos**.

**Etiquetas de artículo** (`service/etiquetasarticulo/`): flujo **independiente
del envío** (`/etiquetas-articulo-produccion`), su única entrada es el excel de
pedido del cliente. `/etiquetas-articulo` es el **menú de la sección** (en
`MenuController`, que es una portada y no un paso del flujo): producción y, sin
implementar todavía, SMS y prototipos. `GeneradorEtiquetasArticuloCliente` es la interfaz, despachada por
clave de cliente; implementado AMI. Una hoja por fila del pedido (= por EAN13),
40 etiquetas idénticas por hoja en una rejilla 4×10 que cabe en un A4, y un
fichero por (tipo, Made in): bolsos MOROCCO, bolsos SPAIN, cinturones
(`UBL*`). **No hay plantilla `.xlsx`**: la maquetación son las constantes de
`RejillaEtiquetas` y `BloqueEtiquetaArticulo` (capa común, `service/etiquetas/`);
`EtiquetasArticuloExcelBuilder` es solo el orquestador. Todo eso está anclado
al fichero real del cliente por `EtiquetasArticuloMaquetacionTest` — POI no
copia el `pageSetup` al clonar hojas, así que heredarla de una plantilla no
servía.

**Procesado de escandallos ICSUITE** (`service/escandallos/`): flujo
**totalmente independiente** del resto (`/clickup`, pantalla «Escandallos para
ClickUp») — no hay envío, ni
cliente, ni catálogo. Entran N excels de escandallo del ERP y sale **un solo
`.xlsx` con una hoja por escandallo** (`Escandallos ICSUITE.xlsx`). Los
escandallos son PDFs convertidos a excel: **los valores no caen en la columna de
su encabezado** (`Article` en B9 pero los códigos en A10, `Quantitat` en X9 pero
las cantidades en W10) y el número de materiales varía, así que `EscandalloReader`
**no usa coordenadas**: localiza la fila `Article…Quantitat`, anota *todas* sus
columnas con encabezado —también `Preu Ult.` e `Imp. Material`, que son las que
impiden que el precio se lea como cantidad— y asigna cada celda al encabezado más
cercano. Ojo: esos ficheros traen celdas `inlineStr` vacías y POI devuelve `null`
en `getStringCellValue()`. Nombre de hoja = modelo + color (`NombresHoja`), porque
hay un escandallo por color y todos comparten `MODEL`. Sin plantilla `.xlsx`: la
maquetación son constantes de `EscandallosExcelBuilder`.

**Entrada por packing list de taller** (`service/taller/`, `/packing-list` modo TALLER): cuarta vía de entrada. El taller manda su propio packing list en excel junto con el material y el programa **regenera el packing desde cero**. Su numeración de cajas, su medida y su reparto en bultos **se descartan a propósito**: son orientativos, y lo que se aprovecha es la información de artículo. Diseño completo en [docs/superpowers/specs/2026-09-05-packing-list-taller-design.md](docs/superpowers/specs/2026-09-05-packing-list-taller-design.md).

Lo que no se deduce leyendo el código:

- **La altura de la caja es la ÚLTIMA dimensión** (`60x40x45` mide 45 de alto). Lo dice el catálogo de taras, donde los cartones comparten suelo `60x40` y varían el tercer número. De ahí salen las pilas del palet y, con ellas, cuántos palets lleva el envío. `MedidaCaja` (en `model/`, no en `service/taller/`, para que `config` pueda usarla).
- **El pedido de AMI ya traía todo lo que hacía falta** y nadie lo miraba: la columna `Commandé` (cantidad pedida) y el sufijo del PO (`07704 CH`), que es la destinación y que `AmiPedidoExcel` ya separaba para las etiquetas. El mapa sufijo→destinación está en `application.yml`; un sufijo desconocido es **bloqueante**.
- **Un artículo es UNA fila en el ajuste** (`FilaDigerida.fusionar`): el taller escribe el mismo `referencia + color + talla` en varias filas —una por destinación suya, o dos entregas del mismo color— y todas se fusionan. Lo **recibido se suma** (son unidades físicas), pero la **cantidad objetivo de una destinación NO**: la dice el pedido del cliente, que habla de la referencia y la destinación, no de cuántas veces la haya escrito el taller. Sin la fusión cada fila leía el pedido entero y el objetivo salía multiplicado por el número de filas — en la hoja real, 466 unidades recibidas contra 932 repartidas. Las destinaciones que una fila trae y la otra no **sí se añaden** (el caso del cliente sin excel de pedido, donde la destinación la pone cada fila), y una destinación repetida con cantidad **cero cede** ante una de verdad, porque el cero es lo que vale una sugerencia de PO copiado de una fila hermana. Para que esa regla se sostenga también sin pedido, `objetivosDelPropioTaller` **suma por (artículo, destinación) antes** de repartir, no al fusionar: así el objetivo siempre es una propiedad del artículo y el destino, como en los clientes que sí traen pedido.
- **Repartir más unidades de las que han llegado BLOQUEA** (`DigestionTaller.repartosImposibles`), no avisa: no se puede empaquetar lo que no está en el almacén, y dejarlo pasar no lo arregla —`RepartoDestinaciones` recorta por prioridad y sirve de menos a las destinaciones de abajo—, así que el packing saldría plausible y con menos unidades de las que dice la pantalla de ajuste, y nadie lo vería hasta comparar los dos documentos. Se **recalcula al pintar** y no se guarda en `getBloqueos()`, porque depende de lo que el usuario acaba de teclear: un bloqueo fijo seguiría ahí después de corregirlo y la pantalla se quedaría sin salida. Y **no apaga el botón de generar** (`puedeIntentarGenerar` en el controlador, aparte de la lista de `bloqueos`): se corrige tecleando en esa misma pantalla, así que hay que poder volver a darle: apagarlo obligaría a descubrir que primero hay que pasar por Previsualizar. Repartir **de menos** sigue siendo legal (lo que sobra se queda para la siguiente entrega, y eso ya se avisa).
- **En AMI el color se cruza por código, por nombre o por los dos** (`AmiPedidoExcel.casaColor`, que usan tanto la entrada por taller como las etiquetas): el pedido separa el código (`COLORIS` = `221`) del nombre (`Libellé coloris` = `DARK COFFEE`), pero quien rellena la hoja del taller mira la pieza y no el catálogo de códigos, así que escribe `BLACK`, o `221 DARK COFFEE`, o `221`. Las tres formas casan; sin esto la hoja real del taller no encontraba **ni una** línea del pedido. Lo que **no** casa es la forma pegada (`221DARK COFFEE`), y es a propósito: hay códigos de solo dígitos (`221`) y códigos que empiezan por letra (`A237`), así que sin separador habría que adivinar dónde acaba el código, y un color mal partido casa con otra fila y estampa el EAN de otro artículo. Los espacios de más sí se perdonan. El nombre separa las filas igual de bien que el código porque dentro de una referencia dos colores no comparten libellé.
- **En APC el `CODE` de tres dígitos basta**: un `Document d'achat` es una destinación, un artículo y un color, con una fila por talla. Por eso no hay que cruzar por color, que en el pedido es un código (`LZZ`) y en la hoja del taller un nombre (`CAMEL`) — emparejarlos exigiría el catálogo de colores del cliente.
- **Tres cosas separan cajas SIEMPRE** (`AgrupadorCajas.claveDeGrupo`), gobierne lo que gobierne el `TipoMezcla` del cliente: la destinación, el **cartón** (la caja *es* un cartón concreto, no una capacidad abstracta) y el **tipo de artículo** — un bolso y un cinturón no comparten bulto ni con `LIBRE`. El tipo se reconoce con `CajaData.esCinturon(referencia)` (prefijo `UBL`), que es el mismo estático con el que `AmiGenerador` elige entre la plantilla de bolsos y la de matriz de tallas: decidirlo aquí de otra forma partiría un bulto entre dos packing lists.
- **La talla NO separa cajas**: las tallas de una misma referencia y color comparten bulto, y deben hacerlo cuando ahorra un cartón. Cada talla es un artículo con su propio EAN, pero darle caja propia dejaría media caja vacía por talla y una referencia de cinturón se sirve en cinco o seis a la vez. Por eso `NINGUNA` significa "una referencia y un color por caja", no "y una talla".
- **Se mezcla solo si ahorra una caja**: se comparan `Σ ceil(qᵢ/capᵢ)` (puras) contra `ceil(Σ qᵢ/capᵢ)` (mezcladas) y en empate ganan las puras, porque un bulto mixto complica la etiqueta y el packing list. En una caja mixta cada unidad ocupa `1/unidadesPorCaja`: contar unidades sueltas metería doce bolsos grandes donde caben diez.
- **Ese segundo recuento es una COTA, no una promesa**, y ahí estaba el fallo que se arregló: con artículos de capacidades distintas el llenado voraz no siempre la alcanza (ocho unidades de a `1/10` no rellenan el hueco que deja una de `1/3`), así que se contaba lo prometido y se entregaba otra cosa —a veces el mismo número de cajas, pero mixtas—. Ahora se cuenta lo que de verdad ha salido y, si no ha ahorrado un bulto, **se vuelve a cajas puras**; dispara en ~2,4% de los grupos donde la cota decía que había ahorro.
- **Dentro de un grupo mezclado se empaqueta por unidad más voluminosa primero** (`porUnidadMasVoluminosa`, orden **estable**). Sin ese criterio el resultado dependía del orden en que llegaran las filas —las unidades menudas llenaban las cajas, la grande ya no cabía y hacía falta un cartón más—; el orden estable conserva "agotar los colores de una referencia antes de empezar otra" entre artículos que ocupan lo mismo.
- **El reparto dentro de un artículo es equitativo**: 31 unidades con 10 por caja son 8+8+8+7, nunca 10+10+10+1 (una caja casi vacía se aplasta con el peso de las de encima). Ojo con el orden de los pasos: **la equidad nunca añade cajas**, porque primero se fija `ceil(cantidad/capacidad)` y solo después se reparte dentro de ese número. Lo mismo vale en un grupo mezclado: si el voraz se pasa de la cota, se vuelve a repartir sobre las cajas que de verdad hacen falta, para que el sobrante no acabe en una última caja al diez por ciento.
- **El peso bruto es opcional y es el de una CAJA LLENA** (campo por referencia en la pantalla de ajuste). Una caja llena se lo lleva tal cual; una que va a medias **escala solo la mercancía**, porque el cartón pesa igual vaya lleno o no: `peso = tara + (declarado − tara) × unidades / unidadesPorCaja`. Hay que escalar y no copiar porque, con el reparto equitativo, **casi ninguna caja sale llena** (25 unidades de a 10 por caja son 9+8+8): copiarlo lo pondría igual en las tres y aplicarlo solo a las llenas no lo pondría en ninguna. Es la misma cuenta que haría `WeightInferenceService` si tuviera una caja llena de la que aprender. Dos casos se quedan **sin peso y con aviso**, nunca con un número inventado: un **bulto mixto** (el peso declarado es de un solo artículo) y un **cartón sin tara** (sin ella no se puede separar cartón de mercancía). Por eso `GeneradorPackingTaller` recibe `CatalogoTaras`. El peso **se recuerda entre entregas**, en neto (ver la sección de memoria), así que la segunda vez ya sale puesto.
- **Avisos que se retiraron a propósito**, y por el mismo motivo: saltaban en todas las ejecuciones, así que no informaban de nada y empujaban hacia abajo los que sí hay que leer. Son (1) *la hoja del taller trae filas de otro cliente* —el taller trabaja para varios y manda una sola hoja, o sea que es lo normal— y (2) *el cliente de los datos de entrada no es el del desplegable*, que era informativo y sin nada que hacer al respecto porque el desplegable manda. Lo que **sí** sigue parando el envío es que no quede ninguna fila del cliente elegido. En la revisión, los avisos de importación van **sin el prefijo "Importación:"**: quien lee la pantalla no sabe qué es eso y la palabra repetida se comía el principio de cada línea (los de palets y pesos sí lo llevan, porque ahí dice a qué columna ir a mirar).
- **El número de pedido se ve y se edita por destinación** en la pantalla de ajuste (1b), junto a la cantidad. Los dos clientes ya lo extraían de su excel —AMI el PO (`07704`, sufijo de destinación aparte), APC el `Document d'achat` (`4100128863`)— pero no se enseñaba en ningún sitio, así que no había forma de corregirlo ni de ponerlo donde el pedido no lo trae. Cómo se rotula el campo es **configuración**: `etiqueta-pedido` en `packing-list.clientes`, con `Nº pedido` por defecto; quien teclea tiene delante el documento del cliente, no el vocabulario del programa. Un campo vacío significa **"no tocar"**, como en la revisión, así que se puede corregir solo el pedido sin volver a teclear la cantidad.
- **Una hoja de taller con varios clientes no bloquea**: el taller trabaja para todos y manda una sola hoja, así que las filas de otros clientes **se apartan con un aviso** y no entran en el packing (`DigestionTallerService.soloLasDelCliente`). El nombre se compara sin puntos ni espacios (`A.P.C.` = `APC`) y contra la clave y el nombre del catálogo. Lo único bloqueante es que **no quede ninguna fila** del cliente elegido: ahí el cliente o el fichero están mal, y un packing vacío en silencio sería peor.
- **Hijas y padres**: el reparto y la prioridad se evalúan sobre la destinación **hija** (`CHINE FRANCH` se sirve de las primeras), mientras que el **fichero, la hoja, la dirección y la numeración** van por destinación **padre** (`WHOLESALE`), que es la que acaba en el packing list. La altura la hereda la hija de su padre si no declara la suya.
- **Ni las cajas ni los palets mezclan hijas**: `AgrupadorCajas` agrupa por hija y `GeneradorPackingTaller.apilarPorDestinoHijo` apila por hija, así que `WHOLESALE` y `CHINE FRANCH` salen en el **mismo excel y con numeración seguida** pero **nunca en el mismo bulto ni en el mismo palet**, ni con `LIBRE`. En el almacén se reciben por separado y un palet mixto habría que deshacerlo al llegar. Cuesta cartones y palets —dos hijas con tres cajas cada una llenan dos palets donde cabría uno— y es a propósito. Cada hija se apila además con **su** altura útil, no con la más baja de todas: al no compartir palet, lo que aguante una no limita a la otra. El resumen de pantalla sí enseña la más baja, porque tiene una sola línea por destinación padre.
- **La numeración es el último paso**, palet a palet y pila a pila, para que cada palet ocupe un rango contiguo por construcción. Sin eso `PaletAssignmentService` no podría reasignar los palets al importar el `EnvioInput` generado, y media docena de cajas se quedarían sin palet sin que nada avisara. `numeracion-cajas: CONTINUA` numera seguido **las cajas y también los palets**: con las cajas 1-135 seguidas entre destinaciones, dos palets llamados "1" serían dos bultos físicos con el mismo número en el mismo envío (y en la revisión la columna PALET volvería a 1 en cada destinación, que es justo lo que parecía un fallo). Con `POR_DESTINACION` reinician los dos, porque cada destinación de APC es una entrega aparte.
- **El lector del taller manda por cabecera, nunca por contenido** (`TallerColisExcel`). Deducir la columna de lo que hay escrito debajo da un packing con números plausibles y equivocados, y eso no lo detecta nadie hasta el almacén. Los títulos vienen con acentos, con la "o" voladita de `Nº` y **partidos en dos líneas** dentro de la celda (`"QTITE /\nCOLIS"` en el fichero real): de eso se encarga `normalizar`.
- **`unidadesPorCaja` es `Integer` y `null` significa "no se sabe"**, que es lo que bloquea la generación. Nunca un cero ni un centinela: un valor de relleno se acabaría dando por bueno.
- Todo lo demás —alturas por destinación, prioridades de reparto, reglas de mezcla, numeración— es **configuración** en `packing-list.taller` de `application.yml`.

**Memoria de referencias y taras en base de datos** (`persistence/`, H2 embebida en `./datos/`): la memoria guarda qué cartón, cuántas unidades por caja y **cuánto pesa la mercancía de una caja llena** de cada `cliente + referencia` (el **color no** forma parte de la clave: todos los colores de una referencia se empaquetan igual). Se escribe **al generar**, no al ajustar, y solo las entradas completas. Del peso se guarda el **neto y no el bruto que se teclea**: el neto es del artículo y no cambia, mientras que el bruto lleva dentro la tara, que se corrige cada vez que se vuelve a pesar un cartón y que cambia entera si la referencia pasa a otra caja; guardando el neto, el bruto se recompone siempre con la tara buena del momento (`DigestionTallerService.netoDe`/`brutoDe`). Sin tara conocida **no se guarda peso**, antes que guardar un neto que en realidad es un bruto. Y un peso vacío **no borra** el que hubiera: pesar una caja cuesta bajarla a la báscula y perderlo porque la entrega siguiente se generó sin pesar sería tirar ese trabajo (el cartón y las unidades sí se sustituyen). La tabla de taras se ha movido del yml a la base de datos: `TaraProperties` sobrevive como **semilla** —se aplica solo si la tabla está vacía— y `CatalogoTaras` es la interfaz que consumen `WeightInferenceService` y los controladores. `Main.java` y los tests unitarios siguen usando `TaraProperties` directamente porque no levantan contexto de Spring. Pesar un cartón se hace en la pantalla **`/taras`**. Los tests corren con perfil `test` y base en memoria, fijado en **surefire** y no con `@ActiveProfiles`: a un `@SpringBootTest` nuevo se le puede olvidar la anotación y escribiría en la base de datos real del almacén sin avisar.

**Web** (`web/`): asistente de 3 pantallas — `entrada` (pegar JSON o subir fotos) → `revision` (avisos y tabla editable) → `resultados` (descarga individual, ZIP, volcado ERP y etiquetas de caja, todo ya generado). Estado del envío en sesión HTTP (`EnvioEnCurso`).

Un aviso de etiquetas es un `AvisoEtiqueta` con las piezas **sueltas** (destinación, ámbito CAJA/PALET/DESTINO/FICHERO, número, hecho, consecuencia), no una frase montada, y lo comparten los dos generadores a propósito: **el formato de un aviso es una sola decisión, no una por cliente**. Van sueltas porque la pantalla necesita cada una por su lado —resalta la consecuencia, agrupa por destinación, compacta números y tiñe los de palet— y **la frase no es partible con seguridad**: unos separan hecho y consecuencia con `.`, otros con `;` y los de `FilaPedido.avisosEan` con `:`. `texto()` reconstruye la frase de siempre (juntando con `". "`) para quien solo quiera leerla; `ResultadoEtiquetas.getAvisos()` es esa vista derivada y de solo lectura, mientras que `getDetalle()` es la lista que se rellena. Sin vocabulario técnico —"la entrada", nunca "el JSON"—: quien los lee no sabe de qué formato salieron los datos.

**Los avisos de etiquetas se agrupan al pintarlos, no al generarlos** (`AgrupadorAvisosEtiquetas`, capa web): el generador emite uno **por caja**, que es la verdad del envío, pero leídos así son la misma frase repetida tantas veces como cajas y eso entierra los que sí hay que atender. En pantalla, cada destinación es un `<details>` con separación propia; a la vista quedan el recuento y la **consecuencia** en negrita ("3 cajas · etiqueta sin EAN13 ni EAN128") y el hecho largo que la causó se pliega. Tres reglas: el **resumen agrupa por consecuencia** y no por hecho (dos referencias que faltan son, en resumen, dos cajas sin EAN; el detalle sí las separa), cuenta **números distintos** —una caja con dos problemas suma en las dos líneas, pero el mismo problema repetido en ella no la cuenta dos veces, que pasa porque `resolver()` corre una vez por talla— y los **rangos no rellenan huecos** (`Cajas 1-2, 5`, nunca `1-5`), igual que en la tabla de revisión: una línea compactada nunca dice algo que no sea cierto de todas sus cajas. Es `<details>` nativo y no JavaScript porque en `/resultados` no hay formulario que se pueda pisar. El tinte propio de los avisos de palet y el margen entre destinaciones viven solo en el CSS, así que los ancla `RutasTest` leyendo el fichero.

Las cajas en la revisión se localizan por **posición** (`indicesCaja`), no por número de caja, porque los números pueden repetirse (cajas mixtas).

En la revisión **todos los campos son editables** (`RevisionForm.CajaEditada`, inputs `cajas[i].*`), no solo los pesos: la extracción por fotos puede leer mal cualquier dato y esta es la pantalla donde se corrige. Reglas: un campo que llega **vacío significa "no tocar"** (así que se puede sobrescribir cualquier valor, pero no dejarlo en blanco); los dos pesos siguen saliendo solo en la **línea líder** de cada caja física; un **bulto mixto** (varios artículos o varias tallas, `FilaCaja.bultoMixto`) edita su peso a mano pero **no ofrece el botón "recalcula peso"** (`FilaCaja.puedeRecalcularPeso`), porque ese peso es el de varios artículos juntos y no hay peso por unidad que propagar al resto del modelo — el botón prometía un cálculo que ahí no se puede hacer; corregir el **tamaño** cambia la tara y por eso se re-infiere el envío entero tras cada edición; y editar el **palet** solo recalcula la lista de "sin palet" leyendo el dato — **no** se vuelve a ejecutar `PaletAssignmentService`, cuyos rangos son los del JSON original y machacarían lo tecleado a mano.

La tabla de revisión va **compactada** (`AgrupadorFilasRevision`): un tramo de cajas consecutivas equivalentes se pinta en una sola fila con el rango en la columna CAJA (`4-8`), y esa fila manda un índice por cada caja del tramo, así que lo tecleado se aplica a todas. Regla del criterio de agrupación: **una fila compactada nunca muestra un valor que no sea cierto para todas sus cajas** — cualquier diferencia en referencia, color, PO, cantidad, tamaño, palet, pesos o *talla* parte el grupo, y las cajas mixtas no se compactan. Ojo al escribir tests de esto: con una tara conocida la inferencia rellena el resto de la referencia por su cuenta y **enmascara** un fallo de propagación; usar un tamaño sin tara para probarlo de verdad.

La columna TAMAÑO es un **desplegable** con las taras de `application.yml` ordenadas de mayor a menor **por volumen**, no alfabéticamente (`TaraProperties.tamanosDeMayorAMenor`; `100x40x40` es la caja más grande y como texto iría antes que `40x30x20`). Un tamaño que **no** esté en el catálogo se añade como opción propia marcada `(sin tara)` y ya seleccionada: si solo se ofreciera el catálogo, el navegador elegiría el primero por su cuenta y guardar la fila cambiaría el tamaño del envío en silencio.

Las filas van **teñidas por palet** (`FilaCaja.bandaPalet` → clase `tr.palet-N`): cada valor de palet de la destinación toma un matiz de la paleta de quince tonos del CSS, y toda destinación arranca por el primero. La banda va por **orden de aparición del valor**, no por `numeroPalet % 15`: con el número crudo, dos palets separados por quince exactos (1 y 16) caerían en el mismo color y el cambio dejaría de verse justo donde se busca; ligarla al valor y no a la fila hace además que un palet que reaparece más abajo recupere su color. Los quince tonos son una rueda de matiz a **claridad constante** (OKLCH `L=0.972 C=0.024`): cambia el color, no la luminosidad, así que ninguna fila parece más resaltada que otra. Una caja **sin palet** no se tiñe, y `AgrupadorFilasRevision.BANDAS_PALET` y el número de reglas `tr.palet-N` tienen que seguir cuadrando. El amarillo de "le faltan pesos" tiñe **solo las dos celdas de peso** (`tr.pendiente td.celda-peso`) y no la fila entera: teñir la fila la lavaba por completo —misma especificidad y va después, así que ganaba— y en un envío **generado desde el packing del taller**, que llega sin ningún peso a propósito, eso tapaba la banda en **todas** las filas; la banda estaba en el HTML y no se veía ni una. Teñir solo la celda que falta además señala qué hay que rellenar. `RutasTest` lo ancla leyendo el CSS, porque desde el código no se ve.

Los estáticos se sirven con **hash del contenido en el nombre** (`/estilo-a1b2c3.css`, `spring.web.resources.chain` en `application.yml`, anclado por `RutasTest`). Sin eso el navegador reutiliza el CSS viejo tras cada cambio de estilos y parece que la hoja no se aplica; es un fallo invisible desde el código.

El número de caja de un tramo compactado no se teclea: la fila se **despliega** con el triángulo (`▶`/`▼`), que es un `POST /alternar-fila?destino&indice` — un submit del mismo formulario, así que aplica lo tecleado antes de recargar. Qué filas están desplegadas vive en la **sesión** (`EnvioEnCurso.filasDesplegadasDe`), con clave posicional `(destino, índice de la primera caja del grupo)`; una marca que ya no arranca ningún grupo se ignora. Se hizo por servidor y no con JavaScript **a propósito**: si despliegas, cambias un dato de una caja y vuelves a plegar, `sonEquivalentes` deja las filas separadas por su cuenta y ningún valor se pisa en silencio. `section.destino` no lleva `overflow-x` por el mismo cuidado: convertiría la sección en el contenedor de scroll y rompería las cabeceras sticky.

## Reglas del proyecto

- **Nunca fallar en silencio, nunca bloquear por datos que un humano puede resolver**: los servicios devuelven DTOs de resultado con avisos (`EnvioImportado`, `ResultadoAsignacion`, `ResultadoInferencia`, `ExcelGenerado.cajasPendientes`) en vez de lanzar excepciones. Un excel con pesos pendientes se genera igual, con las celdas en blanco.
- Los pesos son `Double`, no `double`: `null` significa "desconocido" y es lo que dispara la inferencia y las celdas vacías. No cambiar a primitivo.
- El JSON puede traer `pesoBruto` (kg) **opcional** por caja cuando la imagen lo indica; si viene se usa tal cual (y la inferencia solo deriva el neto = bruto − tara), si falta se infiere como siempre. El peso neto nunca viene en el JSON.
- **`medidaCaja` es obligatoria en el papel pero puede faltar de verdad**: se escribe una sola vez por grupo de cajas, a veces de lado en el margen, y el prompt prohíbe copiar la del grupo vecino (una medida inventada acaba en el volumen declarado de un envío real), así que omitirla es la respuesta correcta del modelo. Una medida ausente **no bloquea**: `VolumenUtil.volumenTotalM3` la salta —la caja cuenta como cartón pero no suma volumen— y el desglose la rotula `?` en vez de escribir `null` en una celda que lee el cliente. Una medida **presente pero ilegible** (`60x40`) sí lanza: ahí no hay nada que interpretar. El aviso vive en `WeightInferenceService` y **no** en el importador, porque la revisión reinfiere tras cada edición pero no reimporta: solo así desaparece al elegir el tamaño. Y por eso mismo distingue "caja sin medida" (se arregla en la columna TAMAÑO) de "cartón sin pesar" (se arregla en la pantalla **`/taras`**, no en el yml: la tabla de taras vive en la base de datos desde que existe esa pantalla): mandar al usuario a editar un fichero por un dato que se teclea en pantalla es peor que no avisar.
- **Un peso por caja física, en su primera línea** (`model/CajaFisica`): una caja puede ocupar varias líneas del JSON (tallas, colores, referencias) pero se pesa una sola vez y ese peso es el de su **línea líder**; las demás no aportan peso y una caja está pendiente si su líder no lo trae. Vale para todos los clientes y para packing lists y etiquetas: **nunca sumar las líneas de una caja**. Ojo a la diferencia entre *dónde vive* el peso y *dónde se escribe*: un bulto compartido por dos artículos sale en **dos packing lists de AMI** (uno por referencia+color) y lleva su peso en **los dos** —es el mismo cartón y uno sin peso no se expide—, pero dentro de cada excel se escribe **una sola vez**, o el `SUM` de la fila de totales lo contaría dos veces. Como el líder puede caer en el excel de otro artículo, `AmiGenerador` resuelve los bultos de la destinación entera **antes** de partir en grupos (`cajaCompartidaPorDosArticulosLlevaElPesoDelBultoEnLosDosExcels` lo ancla). APC y GENERIC no repiten nada: ahí las líneas de un bulto son filas consecutivas del **mismo** fichero y la plantilla real del cliente deja en blanco las de continuación.
- Las plantillas de `src/main/resources/client-packinglist/` tienen filas modelo y coordenadas de las que dependen los builders: **no editar la fila modelo ni los encabezados** de una plantilla sin revisar su builder.
- **Todos los JSON de envío del repo son fixtures generados por IA**, no datos de cliente: los de `src/test/resources/ejemplos/`, el `packing_list_ami_test.json` del `Main` y los recortados dentro de los documentos de `docs/`. Se escribieron sin conocer la realidad del almacén (cajas, unidades, pesos, medidas y palets puestos a ojo) para pruebas visuales del usuario y como fixture. **No deducir de ellos cómo son los datos reales de un cliente ni citarlos como evidencia.** Única excepción parcial: las claves (referencia, color, talla, PO) de `envio-ami-bags-y-belts.json` sí se copiaron del pedido real de AMI, correspondencia que **ningún test verifica**.
- **Los únicos datos reales de cliente son los dos excels de pedido**: `docs/Etiquetas cajas/EAN PUNTOTRES H26.xlsx` (AMI, copiado a `src/test/resources/ejemplos/`) y `docs/Etiquetas cajas/APC_PEDIDO_FALL26.xlsx` (APC, copiado también a `src/test/resources/ejemplos/`, lo lee `ApcPedidoExcel`). De los demás `.xlsx` de `docs/` lo real es la **maquetación** (plantillas y salidas del cliente), no el contenido. Ver [src/test/resources/ejemplos/README.md](src/test/resources/ejemplos/README.md).
- `Main.java` se mantiene como prueba manual por petición explícita del usuario; no eliminarlo aunque la web cubra el mismo flujo.
- Los tests instancian los servicios con `new` (JUnit 5 puro) por defecto; solo levantan contexto Spring con `@SpringBootTest` los que necesitan cableado real que no se puede replicar a mano: los de la capa web (mapeo de rutas, redirecciones, MockMvc) y los que verifican los JSON de ejemplo contra el catálogo real de `application.yml` (`EjemplosJsonTest`). Los tests de builders reabren el `.xlsx` generado con POI y comprueban celdas reales — seguir ese patrón.
- **La tabla de taras es un dato del almacén, no una constante del programa**: entran tamaños nuevos y los pesos se corrigen a medida que se pesa cada cartón (los que aún no se han pesado están puestos a `0.01`, y el programa tiene que funcionar igual). Por eso **ningún test fija un valor de `application.yml`**: `PackingListControllerTest` declara las suyas en `@SpringBootTest(properties = ...)` porque lo que comprueba es la aritmética de la inferencia, y `PackingListApplicationTest` comprueba que el yml se enlaza y que las claves se normalizan, nunca cuánto pesa un cartón. Escribir `assertEquals(0.6, ...)` contra el yml convierte pesar una caja en un cambio de código y deja media docena de tests en rojo por algo que no es un fallo.
